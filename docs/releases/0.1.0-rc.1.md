# Dockplane 0.1.0-rc.1

The first release candidate. It is feature-complete for 0.1 and has been
installed, upgraded, backed up and recovered on real machines. It is a
candidate rather than a release because a few things are still open — they are
listed at the end.

## What Dockplane is

A self-hosted control plane for Docker across several Linux hosts. One place to
see what is running everywhere, start, stop and restart a container, read its
logs live, and know who did what.

It is deliberately narrow. Dockplane manages Docker and the operational
environment around it. It is not a datacenter platform, a Kubernetes tool or a
general-purpose remote shell.

## Supported platforms

| | |
| --- | --- |
| Control plane | Ubuntu 24.04, Ubuntu 22.04 or Debian 12, with Docker Engine and the Compose plugin |
| Managed hosts | Debian 12 or Ubuntu 24.04 with systemd. amd64 is supported; **arm64 is experimental** |
| Browsers | Any current browser; the application needs JavaScript and a modern CSS engine |

## Installing

Point a DNS record at the machine, then:

```bash
sudo ./install-control-plane.sh --domain dockplane.example.com
```

The installer checks the host before writing anything, prepares
`/opt/dockplane`, generates this deployment's secrets and its agent
certificate authority, starts the stack, waits until it is serving, and offers
to create the first administrator. On a clean host it takes about twenty
seconds.

Then install `dockplane-agent` on each Docker host, create an enrollment token,
and enroll. See [Installation](../getting-started/installation.md).

## What it does

**Sees.** Hosts with their facts and metrics, containers with state and health,
Compose projects, all discovered by the agent and reconciled so an incomplete
pass never deletes something that still exists.

**Operates.** Start, stop and restart a container. Each is a separate
permission, confirmed before it runs, serialised per container, recorded as an
action and in the audit trail, and answered with the state actually observed on
the host afterwards.

**Explains.** Live container logs — a snapshot and then a stream that follows —
with stdout and stderr kept apart and every bound made visible when output is
dropped. An audit trail of every security-relevant and infrastructure-changing
event, with actor, target, result and request identifier.

**Protects.** Local accounts with Argon2id password hashing, TOTP multi-factor
authentication with single-use recovery codes, server-side sessions that can be
revoked, login throttling, and permissions enforced by the control server
rather than by what the interface happens to show.

## The security model in one page

Each managed host runs an agent with its **own identity**: a private key
generated on that host, never transmitted, and a certificate issued by an
internal authority in exchange for a single-use enrollment token. The agent
connects **outward** to a mutual-TLS gateway on port 9443, where the control
server derives its identity from the certificate it presents. Nothing needs to
reach into a managed host, and revoking one agent affects only that host.

There is **no shell, no exec and no arbitrary command execution.** The agent
implements ten named capabilities, fixed at build time. Three of them change
anything — start, stop, restart — and each takes a container identifier and
nothing else.

The agent needs access to the Docker socket, which is **equivalent to root on
that host**. That is unavoidable for managing Docker and is precisely why the
agent has no way to run a command.

Browser TLS and agent TLS are **separate trust domains**. The proxy terminates
the browser's certificate on 443; it never touches 9443, because a proxy
terminating that connection would replace every agent's identity with its own.

**Container logs may contain anything an application prints**, including
secrets. Reading them is a permission of its own for that reason. Log content
is never stored, audited, or written to a server log.

**Backups contain this deployment's private keys.** See below.

## Upgrading

```bash
sha256sum -c SHA256SUMS
tar xzf dockplane-<version>.tar.gz
cd dockplane-<version>
sudo ./install-control-plane.sh --domain dockplane.example.com
```

The installer is the upgrade. It recognises the deployment that is already
there, takes a backup before it changes anything, replaces the Compose file and
the Caddyfile with this release's, migrates the schema before the containers
change, and records the new version only once the result is serving.

A release can change more than an image tag — a new setting has to reach the
container that reads it — so upgrading by pulling images and editing `.env` is
not enough and is not the supported path.

Secrets, the certificate authority, the database and an operator's own settings
are kept. Running the migration before replacing the containers means a failed
schema change leaves the previous version serving.

Agents are upgraded separately with `dpkg -i`, keep their identity, and need no
re-enrollment.

## Backups

```bash
sudo /opt/dockplane/dockplane-control backup /var/backups/dockplane-$(date -u +%Y%m%dT%H%M%SZ)
```

Takes the database, the application encryption key, the agent certificate
authority and Caddy's certificates. Without all of those a restore is not a
restore: the encryption key is what makes stored second factors readable, and
the authority is what makes every enrolled host recognisable.

> **The backup is not encrypted.** It contains the agent certificate
> authority's private key and the application encryption key. Anyone who reads
> it can impersonate every managed host. Keep it on encrypted storage.

Restoring has been verified end to end: a destroyed control plane, rebuilt from
the installer and a backup, served HTTPS on the same certificate, accepted the
administrator's existing second factor, and had its agent reconnect in five
seconds without enrolling again.

## Known limitations

- **arm64 is experimental.** The images and the agent package are built for it
  and their contents are checked — architecture, linking, package metadata —
  but no arm64 machine has run them. Nothing about arm64 in this candidate is
  a runtime claim. Use amd64 in production.
- **Backups are unencrypted.** Deliberate for 0.1; the alternative was
  introducing cryptography late in a release cycle.
- **Re-enrolling the same machine creates a new host record.** The previous one
  stays in the inventory marked revoked, and every operation against it is
  refused. Two entries for one machine is confusing but not dangerous.
- **No automatic updates and no APT repository.** Upgrades are explicit.
- **No shell, exec or arbitrary command execution**, and Compose projects are
  read-only. Both are product decisions, not gaps.
- **Container removal, volume deletion and image management are not
  implemented.** Destructive Docker operations were left out of 0.1
  deliberately.
- **The agent must reach the control plane at the hostname it was enrolled
  with.** Moving the control plane to a different hostname requires enrolling
  every host again.
