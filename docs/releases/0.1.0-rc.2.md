# Dockplane 0.1.0-rc.2

The second release candidate. It adds one thing an operator asked for — adding a
host without reading a manual — and fixes two things the first candidate got
wrong, one of which would have made upgrading to this release impossible.

## Adding a host

`Hosts → Add host` now produces a single command to run on the new machine:

```bash
printf '{"ticket":"%s"}' '<ticket>' | curl -fsS --data-binary @- \
  -H 'content-type: application/json' \
  https://dockplane.example.com/api/v1/host-setups/bootstrap | sudo bash
```

It checks what the machine is, downloads the agent package that matches this
control plane, verifies it against the checksums published with that release,
installs it, enrolls the host and starts the service. The interface then shows
what the control plane has actually observed — the command was run, a
certificate was issued, the agent is connected, the inventory arrived — and
nothing else. There is no progress bar counting up to a state nobody has seen.

Docker Engine has to be there already. Nothing else is installed and nothing
else is changed.

### Two credentials, and why

The command carries a **bootstrap ticket**: 256 bits of random material, stored
only as a digest, spent by a single atomic claim so two machines racing with the
same command cannot both be served, and dead after ten minutes, a cancellation
or a regeneration. It travels in the request body rather than in the address, so
no proxy or access log on the way records it.

What the agent enrolls with is the **enrollment token** — the same one-time
credential as before, unchanged. It never appears in the visible command, in an
argument list, in the environment or on disk: the installer hands it to the agent
on standard input.

> **The bootstrap ticket can survive in your shell history.** It has to reach the
> machine somehow, and a command you paste is how. That is why it is short-lived
> and single-use. Until it is used, treat it as a password.

No host record is created before a machine exists. A setup holds the intent; the
host and the agent are created by enrollment exactly as they always were.

## Upgrading

**The installer is now the upgrade.** Download the release, check it, unpack it,
run it:

```bash
sha256sum -c SHA256SUMS
tar xzf dockplane-0.1.0-rc.2.tar.gz
cd dockplane-0.1.0-rc.2
sudo ./install-control-plane.sh --domain dockplane.example.com
```

It recognises what is installed, takes a backup and refuses to continue without
one, replaces the Compose file and Caddyfile with this release's, migrates the
schema before the containers change, and records the new version only once the
result is serving. Secrets, the certificate authority, the database and settings
you added are kept.

**The upgrade path documented for 0.1.0-rc.1 does not work.** Pulling images and
editing `.env` never adopted a new Compose file, so a setting a release
introduces never reached the container that reads it. That instruction has been
removed. Upgrading from rc.1 to this release uses the installer above.

## Fixed

**The search overlay was laid out on every page, even closed.** It set `display`
unconditionally, which overrode the browser's rule for a closed dialog, so it sat
in the document flow below the content — out of the top layer, without a
backdrop — and appeared to jump when opened. Measured before and after in Firefox
and Chromium at four viewport sizes.

**The installer named the wrong release.** It carried the version it was written
for as a constant rather than reading the bundle it ships in, so a newer bundle's
installer went looking for the release it was meant to replace and failed on an
image that is not there.

**The pre-upgrade backup was reported but not taken.** The backup library is
sourced by `dockplane-control`; run directly it does nothing and exits zero, and
the installer trusted that exit status. It now goes through `dockplane-control`
and the result is read back by the validation a restore performs — manifest,
format, checksums, database dump, encryption key, certificate authority — before
the schema is migrated. Backups are written to `/var/backups/dockplane`.

**An install command that had stopped working still counted down.** The wizard
computed expiry from the value it was handed; the status the server reports now
takes precedence.

## Supported platforms

| | |
| --- | --- |
| Control plane | Ubuntu 24.04, Ubuntu 22.04 or Debian 12, with Docker Engine and the Compose plugin |
| Managed hosts | Debian 12 or Ubuntu 24.04 with systemd. amd64 is supported; **arm64 is experimental** |

**arm64 is built for and inspected, and no arm64 machine has run it.** Nothing
about arm64 in this candidate is a runtime claim. Use amd64 in production.

## Known limitations

- **Backups are not encrypted.** They contain the agent certificate authority's
  private key and the application encryption key. Keep them on encrypted storage.
- **Re-enrolling the same machine creates a new host record.** The previous one
  stays in the inventory marked revoked.
- **No automatic updates and no APT repository.** Upgrades are explicit.
- **No shell, exec or arbitrary command execution**, and Compose projects are
  read-only. Both are product decisions, not gaps.
- **Container removal, volume deletion and image management are not
  implemented.**
- **The agent must reach the control plane at the hostname it was enrolled
  with.**
- **Images are not signed.** A bill of materials and build provenance are
  attached as attestations, which is not the same thing.
